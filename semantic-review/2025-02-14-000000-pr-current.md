# Native session coaching and machine-profile selection

The change adds load-time recovery for active sessions whose warm-up targets are still null, expands the session selector to global active machine profiles, and makes profile changes trigger isolated coaching. The server now filters coaching context by the selected exercise/profile key and carries profile notes and permitted weights into that request. The warm-up recovery path does call start coaching and persists validated AI or fallback set proposals. **Watch for:** **confirmed** legacy sessions can receive a last-used profile without invalidating coaching and targets that were generated for the unprofiled exercise; **confirmed** the UI offers the global profile selector on non-machine/custom exercises even though the PATCH is rejected by the server.

**Verdict**: NEEDS_CHANGES

## High-level view

The load-time warm-up check is correctly placed after the session snapshot is fetched, and the start-coaching endpoint applies validated proposals to both target and coach-suggested fields. Explicit profile changes use a one-exercise context, so the selected profile’s notes and available weights are isolated from other exercises during that request.

Profile defaults are backfilled server-side from the newest completed session, and the native dropdown combines all active global profiles with exercise-local profile data. The backfill currently changes the exercise identity without invalidating the already-persisted coaching snapshot, while the UI does not gate the selector by equipment type; those two paths can produce stale coaching or a guaranteed 422 response.

### Legacy active sessions keep unprofiled coaching after default selection

`_apply_last_used_profiles_to_session` fills `source_machine_profile_id` and `machine_profile_name` for an active session that has no profile, and the session GET routes commit that change. The frontend then sees the selected profile, but its load-time condition only calls `generateForgeSessionStartCoaching` when `start_coaching` is absent, the stored focus is legacy-detailed, or a warm-up target is missing. If the old session already has a start briefing and non-null warm-up targets, no second request is made. The briefing, `coach_guidance`, and numeric targets therefore remain based on the unprofiled history/context, so the selected profile’s notes and available weights never enter the AI request for that resumed session. **This is confirmed by the backfill mutation in `backend/app/routes/forge.py` and the guarded request in `frontend/src/components/ForgeSessionPage.tsx`.**

The fix should make profile backfill an explicit invalidation boundary. Have `_apply_last_used_profiles_to_session` return the affected session exercises (or otherwise expose that fact), clear each affected exercise’s profile-specific `target_*`/`coach_suggested_*` values and stale `coach_guidance`, set `session.start_coaching = None`, commit, and let the existing loader call `/start-coaching`; alternatively, have the GET endpoint directly run the same start-coaching generation after backfill. The start-coaching request must then build its context from the newly assigned profile before persisting the replacement briefing and proposals.

### Global selector submits invalid profiles for non-machine exercises

`ForgeSessionPage` builds `selectableMachineProfiles` from every active global profile and renders the `<select>` whenever that list is non-empty, regardless of `activeExercise.equipment` or whether the exercise has a library source. Selecting any profile on a barbell, dumbbell, bodyweight, or custom exercise sends `machine_profile_id` to `PATCH /sessions/{session_id}/exercises/{id}`. `_session_machine_profile` deliberately rejects that combination because it requires a library exercise whose equipment is `machine` or `cable`, so the visible control produces a guaranteed error instead of a selectable state. **This is confirmed by the selector condition in `frontend/src/components/ForgeSessionPage.tsx` and the server validation in `backend/app/routes/forge.py`.**

Gate the selector with a `canSelectMachineProfile` condition requiring `activeExercise.source_exercise_id` and equipment in `machine`/`cable`; render the existing profile label when false. Keep the options sourced from `machineProfiles` for eligible exercises so every active global profile remains selectable, including profiles not linked through `available_machine_profiles`.
