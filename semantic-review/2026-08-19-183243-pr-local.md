# Native Forge session discard, history, and completion feedback

This change adds confirmation-gated deletion for active Forge sessions, a completed-session history, derived session duration, target-derived logging defaults, an expanded in-session coach, and visual completion feedback. Completed-session deletion removes the session before recalculating coach data for its source plan; active-session deletion is ownership-scoped and cascades to session-local state. The history view exposes the first page of completed sessions and lets each entry be opened or deleted. **Watch for:** **confirmed** progression metadata is not fully cleared when deletion removes the latest or only relevant history; **confirmed** reopening an old completed session still plays the completion bloom; **likely** history older than the first 50 sessions is inaccessible.  
**Verdict**: NEEDS_CHANGES

## High-level view

Deletion removes the completed session before deriving new native progression for its source plan. That refresh only overwrites fields supported by replacement history, so deletion can leave an obsolete prior-result value in the plan.

History is summarized rather than duplicating each immutable session snapshot, and its duration is derived from persisted start and completion timestamps. The client always requests the endpoint's default 50-item page, however, with no continuation mechanism, so the visible history ceases to be complete for established users.

Target values are now used both as input placeholders and as the default actual values when a set is checked, while the coach panel opens by default. The completion-mark animation is attached to every completed-session render, not solely to a newly completed session.

## Progression recalculation leaves deleted performance visible

**Confirmed:** `delete_session` flushes the deleted completed session and then calls `_refresh_native_coach_targets` for its source plan. The refresh derives history after deletion, but it only assigns `previous_weight_kg` and `previous_reps` when a replacement latest set exists. When deleting the only completed session, `latest_by_name` is empty; when deleting a session that is the only one with a particular trailing set, `latest_sets` is shorter. In both cases the old `previous_*` values remain on `ForgePlanSet`, even though the data that supplied them no longer exists.

The plan's “Vorher” values can therefore disagree with retained completed-session history and show deleted performance. Reset all per-set prior-performance fields before applying the replacement history, then populate only values supported by the recomputation.

## Completion bloom is not limited to a completion event

**Confirmed:** the completion section always renders `<div className="forge-completion-mark">` for `session.status === 'completed'`, and `.forge-completion-mark` always has the `forge-check-bloom` animation. `celebratingCompletion` gates only the enclosing section's pop animation. Selecting any old entry in the new history view therefore triggers the bloom each time its read-only session page mounts.

Keep the static completion mark for historic sessions and conditionally add the bloom class only after the current page's successful completion action.

## The history API is paginated but the history UI is not

**Likely:** the server exposes `limit` and `offset` and caps `limit` at 100, but `ForgePlanPage` calls `listForgeSessions()` once with its default `limit = 50` and renders that array as the entire history. No cursor, offset, total, or load-more action reaches records after that first page.

A user with more than 50 completed Forge sessions cannot find or delete older entries, despite the feature presenting itself as the completed-workout history. Add incremental loading (or an explicitly bounded-history requirement and UI copy) before shipping.
