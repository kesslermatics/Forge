# Native Forge sessions replace the Hevy workout runtime

The cutover routes briefings, session reviews, coaching chat, and analytics through a new projection of completed Forge sessions, while the UI and user API stop exposing Hevy setup. The projection deliberately exposes only completed, actually logged set values, so planned targets are not mistaken for performance. However, the scheduler no longer invokes the retained Forge review generator, leaving no production path that pre-generates tips or unread reviews after a session completes. The unversioned user API also removes fields and endpoints while retaining the encrypted legacy credential with no supported revocation path. Watch for: **confirmed** automatic workout-tip/review generation has been removed; **confirmed** legacy API consumers receive breaking user-contract and endpoint changes; **confirmed** unused Hevy credentials remain stored but cannot be revoked through the API; **likely** duplicate Forge plan names can cause tips to use a different plan’s template.

**Verdict**: NEEDS_CHANGES

## High-level view

Completed Forge sessions are now the single workout-data source for coaching and analytics. The adapter maps only `actual_weight_kg` and `actual_reps` from completed sets, preserving the distinction between a plan and recorded performance.

The asynchronous review worker still knows how to create Forge-native tips, but `start_scheduler` registers only the daily briefing cron. Completing a workout does not enqueue the worker either, so the pre-generated-review feature silently becomes manual-only.

The user-facing application is internally aligned with the removal of Hevy setup, but the backend has made an unversioned contract-breaking change for deployed or third-party clients. The database retains the provider credential even though the removed API makes it impossible for the user to delete it.

Forge plans are addressed by display name when deriving workout tips. Names are not unique per user, even though a completed session carries the authoritative `source_plan_id`, so same-named plans can cross-wire exercise targets.

The new adapter is an untracked runtime dependency, while this cutover adds no focused automated coverage for its data projection or lifecycle. It must be staged and exercised before the imports and behavior can safely ship.

## The workout-review lifecycle is no longer scheduled

`_generate_workout_review_for_user` was converted to enumerate `completed_forge_workouts` and persist tip rows keyed by the native session UUID, but it is unreachable in normal operation. The old `start_scheduler` registered `workout_review_job` every hour; the new `start_scheduler` registers only `daily_briefing_job`. The only caller left is `POST /api/briefing/trigger-review`, and the frontend merely exports `triggerReviewCheck` without any component invoking it. **Confirmed:** a completed session produces neither an unread review nor background tips unless an authenticated caller manually invokes that trigger.

`backend/app/scheduler.py:start_scheduler` should restore a Forge-native, bounded review job with the existing idempotent session-ID lookup, or `backend/app/routes/forge.py:complete_session` should enqueue the work after the completion commit. A periodic reconciliation job can protect against missed completion events. Test completion through to exactly one `WorkoutReview` with tips and verify that retries do not duplicate AI calls.

## Completed-session projection preserves the recorded-performance boundary

`completed_forge_workouts` limits input to sessions marked `completed`, and `_serialize_completed_session` includes only sets where `completed` is true while mapping `actual_weight_kg` and `actual_reps`, never `target_*` values. An attended session with no logged actuals remains visible for attendance and duration but contributes no invented weight or repetition data.

The adapter is currently untracked, yet `aggregator`, `briefing`, and `scheduler` import it. **Confirmed:** shipping the tracked diff alone raises an import error in every converted runtime path. Add `backend/app/services/forge_session_adapter.py` to version control as part of this cutover.

## Forge plan names are not a stable template identity

The adapter’s `forge_plan_template(db, user_id, workout_name)` calls `.first()` after `name.ilike(...)` and orders only by `position`. `ForgeTrainingPlan` has no `(user_id, name)` uniqueness constraint, and the plan create/update routes do not reject duplicate names. Every native workout session already stores `source_plan_id`, but `_generate_workout_review_for_user` discards it and asks for the template by `workout["title"]`. **Likely:** two plans named “Upper” can cause pre-generated advice for one session to contain the other plan’s exercises and targets.

Add an ID-based helper such as `forge_plan_template_by_id`, pass `workout["source_plan_id"]` from `backend/app/scheduler.py:_generate_workout_review_for_user`, and prefer that ID in the live tips route whenever the caller selected a session or Forge plan. If the public tips endpoint must remain name-based, reject ambiguity rather than silently selecting the lowest-position plan. Cover duplicate names, deleted source plans, and ad-hoc sessions with no source plan.

## User API removal breaks existing clients and strands a credential

`UserResponse` and `/user/me` no longer return `has_hevy_key`; the API-key request/response schemas and both `/user/api-key` operations are removed. The current frontend changes remove its direct usage, but this is still an unversioned response and route deletion. **Confirmed:** an independently deployed older web client or API integration loses its configuration status and receives a 404 when attempting an update or deletion. Keep the field as deprecated, provide a migration-aware endpoint response, or version the contract and require clients to move together.

The associated `User.hevy_api_key` model field remains, including existing encrypted values, but users no longer have a supported way to remove an obsolete third-party credential. **Confirmed:** this leaves unnecessary credential retention with no self-service revocation. Add an explicit, audited retirement migration after the rollback window, or preserve a revoke-only endpoint during that window. Do not silently clear values as part of the frontend/API removal without documenting the migration and rollback policy.

## Forge-cutover behavior is untested

There are no tests in the diff and no existing test references to `forge_session_adapter`, native review scheduling, or the completed-set projection. **Confirmed:** compilation cannot prove that a mixed legacy/native `WorkoutReview` table, duplicate plan names, an empty completed session, or a scheduler restart preserves the expected behavior. Add focused adapter and route tests for actual-versus-target set data, dates/heatmap output, review upsert by native UUID, background generation, and API compatibility during the deprecation period.
